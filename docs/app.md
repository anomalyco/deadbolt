# Desktop app

2026-10-22. Plan and first slice of Deadbolt's desktop UI, built in [Rune](https://github.com/anomalyco/rune). Questions for Kit are marked **Open**.

## Architecture

- **A thin client of the agent.** The app speaks the agent's socket protocol, as the CLI does, and starts the agent if none runs. It holds no keys and reads no store files: unlock, items, devices and pairing are all agent requests. Quitting the app leaves the agent (and its unlock) running.
- **`crates/client` (`deadbolt-client`)** holds what both clients need: the protocol types, where the files live (`Paths`) and the client (`call`, `status`, `ensure_running`, `stop`). The CLI wraps it in `crates/cli/src/client.rs`. `Launch { program, version }` says which binary runs the agent; the replacement rule below lets a bundled app coexist with a separately installed CLI.
- **`crates/app` (`deadbolt-app`)** is a workspace member. Rune, rune-kit and rune-theme-opencode are git dependencies pinned to one rev (`8775a52`, on Rune's `dev` branch), bumped deliberately by changing all three `rev`s in `crates/app/Cargo.toml`. `deny.toml` allows that one git source and BSL-1.0 (the Windows backend of arboard, which Rune's clipboard uses). Linux builds link `libxkbcommon` and `libwayland-client`, so they need `libxkbcommon-dev` and `libwayland-dev` (Fedora: `libxkbcommon-devel`, `wayland-devel`); CI installs both.
- **Finding the agent binary:** in an `.app/Contents/MacOS` directory, always `../Helpers/deadbolt`, even when `DEADBOLT_BIN` or PATH points elsewhere. A missing helper is an error, not a fallback. Outside a bundle: `DEADBOLT_BIN`, an executable sibling (Cargo development), PATH, `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`. Finder launches have a minimal PATH, hence the fallback locations.
- **Threads:** one worker thread runs agent requests in order on a current-thread Tokio runtime and wakes the window when a reply lands. A second thread holds the agent's `watch` stream open and posts each change to the same inbox, reconnecting with backoff (100 ms doubling to 2 s) when the agent restarts; it never starts the agent itself. The UI drains both in Rune's `poll`; nothing polls the socket.
- **Live state:** the agent owns locking (idle timeout, `deadbolt lock`, sleep and screen lock) and the app mirrors it. `locked` or the agent stopping goes to the lock screen and forgets every value; `unlocked` from elsewhere enters the vault; `items` for the shown vault refetches the list, keeping the selection, search and scroll, then the selected item's values in place; `watching` (after each reconnect) and `resync` refetch everything.
- **Secrets in the app:** the passphrase fields are Rune's secure single-line `TextEdit` (`TextEdit::secure().single_line()`: dots, no undo history, no copy, cut or IME, text typed with ⌘ or ⌃ held and control characters such as a pasted line break kept out, the text wiped whenever it's replaced or dropped and as an exiting field starts to leave, macOS Secure Event Input while focused). The passphrase leaves the field into a `Zeroizing<String>` (`model::take_secret`) and stays in one all the way to the socket (the protocol's passphrase fields and the request buffer are wiped too). Item values are fetched one item at a time (`item-get`) and wiped when the selection changes, the store locks or the window closes. Copies go through Rune's `Tx::copy_secret`, which writes with clipboard history exclusion (`org.nspasteboard.ConcealedType` on macOS) through one process-wide owner, and clears them after 30 s, or on lock and quit, only if the clipboard still holds them. An export being imported is read on the agent thread into a `Zeroizing<String>` (`deadbolt_client::export::read`) that goes into the `import` request and is wiped with it once sent; the preview and the import each read the file again, so the UI holds only the file's path and the agent's counts (`ImportReport`). Locking or the agent stopping forgets an import wherever it was (`App::forget_import`), and drops its replies.
- **Keys:** the search field and the passphrase field handle their own keys (`on_input_key`) and get focus by rendering with `focused: true`; the window's `on_key` handles ⌘L and ⇧⌘I, and both fields pass the import's ↵ and esc to `App::import_key`. This keeps working when Rune sends keys to the focused element before the window. In the vault, `on_key` also takes the list's keys (↑↓, ↵, ⇧↵, esc; `App::list_key`, shared with the search field) and ⌘F/⌘K, after Settings, the install page and the import view, so they work with focus on a button or nowhere. A click on a row blurs the search (rows aren't focusable), and the row's press hands focus straight back; the search's field spans its whole box (`view::search`, rune-kit's `TextInput` look built from `text_input`), so a press on its icon or padding focuses it, never drags the window, and never blurs it on the way down. With the list hidden, ↑↓ and a search edit open it again, from the import view too; a search edit also closes the import view (as ↑↓ do), unless an import is running, when the selection waits for the import view to go (`on_imported`, `cancel_import`).
- **Look:** Rune's OpenCode theme (`rune-theme-opencode`, pinned with Rune): `kit(dark)` for both windows and every screen, its Inter and IBM Plex Mono registered through `AppSpec::fonts`/`families`. The vault is rune-kit's shell (`rune_kit::shell::SplitView`): the item list is the sidebar (272 pt, 200–312, ⇧⌘B or ⌃⌘S hides it; `App::sidebar`), the search field and Lock sit in the 48 pt toolbar over the detail pane, and the key hints run along the pane's foot. The main window draws under a transparent title bar (`view::CHROME`, traffic lights centred in that band); every other screen gets an empty 48 pt band to drag by, and its Back or Cancel sits in the band past the lights (`Cx::titlebar_inset`). A page with a Back or Cancel centres its panel under the band, and scrolls when the panel is taller than the room left. The wordmark is the theme's sans, semibold and tight. The bolt's strike is the theme's ember scale (9 at rest, a paler step for the flash); the QR tile stays white in both appearances.
- **First run** (`src/onboarding.rs`, `onboarding/{worker,view,qr}.rs`): creating and joining run on their own thread and connection (`onboarding/worker.rs`), beside the request worker, because a join holds its connection for minutes and waits on the person at the screen. The worker reports each stage as it starts, so progress shows only what really happened. It answers the join's code through `deadbolt_client::converse`, whose handler can wait while the socket is still read, so the other device declining ends the wait at once. A device that is set up but holds no vault (a cancelled join) goes back to onboarding without the passphrase step. Cancelling a join while the device is being set up waits for the setup (the agent finishes it even if the app hangs up), so the form never asks for a passphrase that wouldn't be used; a device set up elsewhere meanwhile refuses the new passphrase with a notice instead of keeping the old one silently. The ticket is a capability until it's used or expires: it's held in `Zeroizing` strings, and a copied `deadbolt pair …` leaves the clipboard (if it's still there) when the code shows, the join ends, onboarding is left or the window closes.

## Motion

Rune's runtime already enforces no first-paint animation, reduced motion (travel off, short fade kept; from the system's setting, or `--reduced-motion`) and retargeting mid-flight.

| Change | Who causes it | Motion |
|---|---|---|
| Locked ↔ vault, any whole-screen change | user or agent | whole-state replacement: blur (σ 1.5, text included), scale .96, fade; enter `.3/0`, exit `.24/0`, the new screen enters on the frame the old one starts to leave |
| Typing filters the list, esc clears it | dependent on typing | instant: the new list replaces the old at once (an edit is instant without `animate_edit_layout`; esc uses `Tx::instant`) |
| Any new selection (search, ↑↓, a click, the selected item deleted or synced away), the selected item's fields | user's hand or agent | instant: the title and fields replace in place (↑↓, a row's press and a list that moves the selection use `Tx::instant`; a click while the import view shows still swaps back), and the fields land with their values a frame or so after the title. A list that moves the selection drops the rows it removed at once too |
| Rows a sync adds or removes, the selection staying | agent | rows that stay slide on `.4/0` and never blur; rows that leave or arrive fade in place (blur 3, scale .96, `.3/0` in, `.25/0` out) |
| A list scrolled under its edge | user's hand | the edge fades over 24 pt, only while rows are hidden under it (hidden extent / 15 pt); ↑↓ stop the selected row 24 pt from the edge, and the list's own ends stay flush |
| Copy icon → check | user | in-place replacement `.3/0` |

| Countdown | time | the bar empties on a linear `rune::Tween` run by the render thread, so it needs no app wakes; the app wakes once a second for the text, and only at the clear while the quick panel is hidden. the label sets tabular figures, so its digits keep one width and nothing shakes |
| Unlock error | agent | fades in |
| Command offer | app | rises 12 pt with a fade, like the copy notice; leaves the same way |
| Install page ↔ vault, its states | user | whole-state replacement; the page's body swaps by replacement (install → installed); Copy → Copied in place; errors fade in |
| Hover | pointer | in 0 ms, out on Rune's snap |

## Quick panel

A Spotlight-style panel for the everyday task: press ⇧⌘Space, type, ⏎ copies the password (⇧⏎ the username, a card's ⏎ its number) and the panel goes away.

- **Shortcut: ⇧⌘Space** (Ctrl+Shift+Space off macOS, where the Super chords belong to the desktop). ⌘Space is Spotlight and ⌥⌘Space is the Finder search window on a stock Mac; ⇧⌘Space is free there and is 1Password Quick Access's default, so it's where people already reach. It's registered system-wide on the panel's `App` (`AppHandle::register_shortcut`, `shortcut::register`), so pressing it anywhere toggles the panel (`App::toggle_panel`); the main window owns the choice (`App::hotkey`, `src/shortcut.rs`).
  - **Changing it:** Settings, at the right end of the vault's key hints, holds a `rune_kit::ShortcutRecorder`. A new chord registers before the old one lets go, so a refused chord keeps the old shortcut working, and the recorder keeps it on its keycaps with a red outline and says why under itself in the app's words (`ShortcutRecorder::error_message`, `shortcut::refusal`), naming the chord and, when Rune knows, who holds it ("⌥⌘Space is in use by Finder search.", else "… by another app."). Rune refuses a chord without ⌘, ⌃ or ⌥ (Ctrl, Alt or Super off macOS) before `on_change` ("Add ⌘, ⌃ or ⌥.", "Add Ctrl, Alt or Super."; Shift alone doesn't count), since a bare key would be taken from typing in every app; F1–F24 alone are fine. Backspace while recording clears the shortcut; Reset to ⇧⌘Space appears whenever it isn't the default, and a refused Reset says why the same way. The choice is saved in `app-shortcut` beside the agent config, written beside it and renamed over it (no file for the default, an empty line for none; a line that doesn't parse, or that Rune would refuse for having no modifier (`Shortcut::require_modifier` in `shortcut::load`), falls back to the default). It's the app's own setting, not the agent's.
  - **When it can't be registered** (another app has it, or the desktop has no global shortcuts): a notice in the vault's detail pane says which shortcut and why ("⇧⌘Space isn't available", "Spotlight is using it, …"), with Choose another… (opens Settings) and Not now (until the next launch). Settings says the same under the recorder, which keeps showing the shortcut, with Try again; recording the same chord again also tries again (`ShortcutRecorderState::mark_unregistered`). The holder's name comes from `AppHandle::shortcut_owner`, asked when a chord is taken (`Hotkey::holder`): macOS names its own shortcuts (Spotlight, Mission Control, …, or "macOS"), at the user's remapped chords, and another Rune app gives its title; other apps' grabs, and Windows and Linux, go unnamed ("Another app is using it, …"). While the default is the one that failed, ⇧⌘Space still works inside Deadbolt (`App::shortcut_fallback`, `window::is_shortcut`, checked in `App::on_key`, the search field and the passphrase field); a changed shortcut gets no in-app fallback.
- **Menus (macOS):** "Open Quick Panel" in the app menu, with the shortcut as its key equivalent, and in the Dock menu (`window::menu`, on the panel's `App`; `Windows::set_menu` follows a change). The standard items (About, Services, Hide, Quit) are Rune's default menu, which `set_dock_icon(true)` also installs after a `--panel` start. Windows and Linux have no native menus in Rune (`MenuError::Unsupported`), so there the main window's key hints keep a clickable "Quick panel" hint (`window::entry`).
- **Starting:** `run()` queues the start on the main window (`App::start_shortcut`), which registers the shortcut and sets the menu on the panel's `App`: Rune attaches every window before any queued update runs.
- **`--panel`** (`window::FLAG`, `Windows::start_with_panel`): starts with the panel instead of the main window, with no Dock icon. Once hidden, it stays running for the shortcut; opening the main window (onboarding, the menu) brings the Dock icon and menu back. If the shortcut can't be registered, the main window opens too, since nothing else could bring the panel back. It's kept for scripting and development: headless `--window panel` runs and `tests/place.rs` use it, and it's the way to try the panel without the main window.
- **Window:** a second Rune window (`rune::run_windows`, key `panel`) with its own `App`: its own agent connection, `App::panel` set, started hidden. Rune's launcher panel (`WindowOptions::launcher_panel`): borderless, transparent and non-activating, so it takes keys while the app you were in stays frontmost, the main window stays where it was, it opens on the current Space, and focus goes back to that app when it hides. A `--panel` start runs without a Dock icon (`RunOptions { accessory: true }`), since a regular app activates itself at launch; opening the main window from it brings the icon back (`AppHandle::set_dock_icon`), and the default app menu with it. 680×440 with the card inset 20 pt, placed at each summon centred 160 pt from the top of the display under the pointer (`window::PLACE`, `AppHandle::place`; Rune falls back to the primary display if that one has gone).
- **What it reuses:** the vault view's search field (`view::search_input`), rows (`view::rows`, `list_row`), the passphrase field and unlock error, and the model's filtering, selection and copy-with-countdown. The panel adds only its phases (`Open`, `Copied`, `Closing`, `Hidden`) and its card. It has no install offer or Settings: it never gets an installer, and `App::overlay_key` ignores them in the panel, so its keys stay its own.
- **States:** connecting; the vault (empty search over every item, the first selected); filtering; no matches; an empty vault; locked, with the passphrase field in place and its error; not set up, which points to the main window (⏎ or Open Deadbolt opens it); can't reach the agent, with Try again.
- **Dismissing:** Escape (in the search or the passphrase field too), clicking away (the window losing focus, `App::panel_focus`), the shortcut again, or a copy: the footer's "Copy password" rolls into "Copied, clears in 0:30" for 1.1 s, then the card fades and the window hides. Both times run from the first frame after the event (`poll_panel` sets the deadline), because an event after a pause (a click away handled in `Runtime::update`) arrives before the app's clock catches up. Hiding forgets everything the panel read or was typed (the list, the query, an item's values, a part-typed passphrase) and moves to a new generation: replies still on their way are dropped, and an item's values are wiped when its reply is dropped, read or not (`agent::Values`). Closing or hidden, the panel fetches nothing (`App::panel_away`): of the agent's changes it follows only a lock or the agent stopping, and list and item replies are dropped. Each summon fetches the list again and starts from an empty search and the first item. ⌘L locks only while the panel is open. The copy keeps counting down while hidden (one wake at its end, not every second) and is cleared on time, on lock, or when the app quits.
- **One clipboard:** both windows copy through Rune's one secret owner, and each copy keeps its `SecretCopy` handle. A countdown clears only its own copy at its deadline, and only while the clipboard still holds it (`SecretCopy::clear_now`). A copy the other window has since replaced ends quietly: its notice leaves without "Clipboard cleared". Lock and quit clear the latest copy, whichever window made it.
- **Footer:** what ⏎ does ("Copy password", "Copy number", "Unlock", …), rolling into the copy's line, or replaced by a notice (an item "has no username", an agent error). ⇧⏎ Username shows only for a login with a username.

### Stand-ins

Adopted at Rune `c479f4b`: global shortcuts (`register_shortcut`), `rune_kit::ShortcutRecorder` and native menus. Gone with them: the shortcut that only worked inside Deadbolt (now only the fallback above), the always-shown "Quick panel" hint on macOS, `App::quit_key` (the menu's Quit runs first, and Rune installs the default menu after a `--panel` start), and `window::leave_if_stranded` (a hidden panel with no main window used to exit once its copy was cleared, since nothing could bring it back; now it waits for the shortcut). Rune's exit also clears a held secret copy (menu Quit, ⌘Q, closing the last window), so the app keeps no clear-at-exit guard of its own. Since `78dcd15`, macOS Quit (the menu, ⌘Q, the Dock, logout) runs each shown window's `on_close` once before the process ends, as closing does: the main window's `App::quit` clears the copy, the panel's quit it queues never runs, and the panel's own `on_close` (`panel_closed`) wipes it without quitting again (`tests/panel.rs`, `quitting_from_the_menu_clears_the_copy_once`). A `--panel` run whose main window never opened has no main window hook to run. Resolved at `78dcd15`, with their fallbacks gone: the conflict owner (the notice said only "Another app is using it."), the recorder's wording (the app drew the recorder without its error, losing the red outline, and put its own line under it, `Hotkey::refused`), and headless physical chords that left their modifiers held (the conflict still showed ⌥⌘ held). Resolved at `57986a9`, the last of them: the start no longer hops through the panel's queue (every window attaches before any queue drains), `shortcut::allowed` is gone (Rune refuses chords without a modifier, so F21–F24 now work alone and off macOS the hint names Super too), and the recorder no longer empties itself after a failed start (`mark_unregistered`). Earlier: focus loss (`on_focus`), activation (`launcher_panel`) and placement (`AppHandle::place`), and their stand-ins (the 30 s idle close, the activating window, the primary-display position).

Off macOS, the main window's "Quick panel" hint (`window::entry`) stays, as Rune's menus there are `Unsupported`.

## Breadboard

The main flows, as states (see the PR for the chat version):

1. Launch → agent starting ("Starting Deadbolt…") → locked or first-run.
   - First run → Create → device, vault, passphrase twice → Protecting your passphrase → Creating personal → the bolt throws → empty vault with the CLI guide.
   - First run → Join → device, passphrase twice → Making a pairing ticket → QR + `deadbolt pair …` (Copy command) → other device pairs → 482 913, They match → Receiving personal → the bolt throws → synced vault. They don't match, Cancel or Escape, or the other device declining → the join form with a notice; the device stays set up.
2. Locked: type the passphrase → ↵ → vault, or the error in place.
3. Vault: type "git" → list narrows → ↵ → "Copied, clears in 0:30" → 30 s → "Clipboard cleared" → notice leaves.
4. ⌘L → locked; the clipboard copy is gone.
5. Import: drag `1PasswordExport.1pux` over the window → the drop zone lights → drop → Reading … → "Import from 1Password · 214 new logins · 3 cards" → ↵ → Importing… → the rows arrive, "Imported 217 from 1Password". esc instead, or locking at any point, forgets it.
6. Later: Devices → Add device → paste ticket → both screens show 482 913 → Confirm → device appears in the list.

## Open decisions

1. **Clipboard timeout:** 30 s now. 1Password uses 90 s, KeePassXC 10 s. Configurable?
2. **Where unlock lives:** decided: the agent owns locking (`unlock_timeout`, `lock_on_sleep` in its config); the app has no timer.
4. **Bundling:** decided: ship `deadbolt` inside `Deadbolt.app`, with an optional command link on first run.
5. **Window model:** decided: the main window plus the quick panel (see Quick panel). A menu-bar item is still open.
6. **Live updates:** done: the app follows the agent's `watch` stream.
7. **Weak passphrases:** the form refuses under 8 characters and only warns about weak ones (a rough estimate that flatters dictionary words). Refuse weak ones too?

## Run, test, snapshot

```sh
cargo run --release -p deadbolt-app     # against your agent (starts it if needed)
cargo test -p deadbolt-cli -p deadbolt-app   # the real-agent test uses the deadbolt cargo built (or DEADBOLT_BIN)
crates/app/scripts/snap.sh              # headless PNGs of every scene into crates/app/snaps/
cargo run -p deadbolt-app -- --scene copied --at 2.4 --snap copied.png   # one scene; --theme light, --reduced-motion
cargo run -p deadbolt-app -- --panel                                             # start with the quick panel; hidden, it waits for the shortcut
cargo run -p deadbolt-app -- --window panel --scene filtering --snap panel.png   # a quick panel scene
cargo run -p deadbolt-app -- --window panel --scene empty --script crates/app/scripts/panel-motion.json --frames 240 --trace motion/panel.jsonl   # motion-lint trace: filter, then close
cargo run -p deadbolt-app -- --window panel --scene empty --script crates/app/scripts/panel-copy.json --frames 150 --trace motion/panel-copy.jsonl   # copy (the opening selection's values are loaded; a new one's come from the agent), then close
cargo run -p deadbolt-app -- --window panel --scene empty --script crates/app/scripts/panel-clickaway.json --frames 150 --trace motion/panel-clickaway.jsonl   # filter, then the window loses focus and the card fades
cargo run -p deadbolt-app -- --window panel --scene empty --script crates/app/scripts/panel-scroll.json --frames 240 --trace motion/panel-scroll.jsonl   # ↓ past the list's bottom edge, then ↑ back
cargo run -p deadbolt-app -- --scene settings --script crates/app/scripts/settings-shortcut.json --snap conflict.png   # record a shortcut another app holds (--at 1.2 for recording)
cargo run -p deadbolt-app -- --window panel --panel --frames 2 --script desktop.json --tree tree.json   # where it's placed: a script with "displays" and "pointer"; prints rune-placed, "placed" in the tree
```

Scenes (`--scene`): `connecting`, `failed`, `locked`, `locked-error`, `vault`, `search`, `copied`, `revealed`, `empty` (with the import drop zone), import: `import-hover` (an export dragged over the empty vault), `import-preview`, `import-nothing-new`, `import-error`, `import` (⇧⌘I in a vault with items), and first run: `welcome`, `welcome-set-up`, `create`, `create-typing`, `create-ready`, `create-invalid`, `create-failed`, `creating` (created at 1.2 s, the moment, the vault at 2.7 s), `join`, `ticket`, `code`, `joining` (joined at 0.6 s), `join-declined`, `join-cancelled`, `join-failed`, the command: `command-offer`, `install-command`, `command-installed`, and the shortcut: `settings` (Settings open; another app holds ⌥⌘Space), `settings-changed` (changed to ⌥⌘Space, with Reset), `shortcut-conflict` (⇧⌘Space taken: the notice), `settings-unavailable` (the same, in Settings, with Try again). They use synthetic data. Any tooling run (`--snap`, `--tree`, `--trace`, `--frames`, `--script`, `--scene`, …) gets no agent, and Rune keeps headless runs off the clipboard, so its output can't hold real items. It registers no real shortcut (the panel's default is registered only inside the run, for `{"shortcut": …}` steps) and never reads or writes `app-shortcut`.

## One bundle, one agent

```text
Deadbolt.app/Contents/
  Info.plist                 pw.deadbolt.app; version from Cargo
  MacOS/Deadbolt             Rune desktop client
  Helpers/deadbolt           CLI and background agent
  Resources/Deadbolt.icns    red keyhole, generated headlessly
```

The CLI uses Apple's `Helpers` code-signing location: `MacOS/Deadbolt` and `MacOS/deadbolt` would collide on a case-insensitive Mac disk. The helper is signed first, then the outer bundle. Fonts are embedded in the app binary. Rune currently has no bundle builder in its scripts or examples.

**One rule decides which agent runs**, and the app and the CLI share it (`deadbolt_client::ensure_running`), so two builds never take turns replacing each other's agent:

| The running agent's protocol | What a client does |
| --- | --- |
| the same as its own | reuses it, whatever build started it: the bundled helper, Homebrew or Cargo |
| older | stops it cleanly, then starts its own binary |
| newer | fails without stopping it, naming the agent's program, version and pid, and suggests updating this copy or running `deadbolt agent stop` |

A bundled app always starts its own helper; if that's missing the app says it's damaged and should be reinstalled, rather than falling back to another install. The app's watch reconnection never starts an agent. `deadbolt agent status` shows which build is running.

In development, a rebuilt agent of the same protocol isn't picked up while the old one runs. `deadbolt agent stop` hands over to whichever build runs next; there's no override that replaces a compatible agent. Tests use `DEADBOLT_TEST_VERSION` for another build and `DEADBOLT_TEST_PROTOCOL` for an older or newer agent (`crates/cli/tests/cli.rs`, and fake agents in `crates/client`).

**The command offer lives in the vault.** Nothing about the command appears before the vault opens: not over onboarding, the locked screen or a failure, and leaving the vault (a lock on sleep, say) closes it. Once the vault shows, a card at the bottom of the detail pane offers **Install…** when no `deadbolt` was found, or **Repair…** when the one found links to a Deadbolt that moved. Not now, or opening the install page, answers it for good: `app-command-offered` is written beside the agent config. The same page stays under **Settings** at the end of the vault's key hints. The page replaces the vault with a Back button and its panel centred, like an onboarding step; Install creates the link, confirms it in place and shows the `rm` that undoes it. While Settings or the page is open it takes every key first (Escape closes it, Tab moves between its buttons); nothing reaches the search field or the list behind it. Copy buttons turn into "Copied" in place, then back. Headless scenes (`command-offer`, `install-command`, `command-installed`) never read or write the preference or install a real link.

The installer prefers writable `~/.local/bin`, `/opt/homebrew/bin`, then `/usr/local/bin` directories on the app's PATH. Otherwise it prefers a writable user directory and supplies a copyable `export PATH=…` command. Finder's PATH may differ from the terminal's; the app doesn't execute shell startup files or change shell profiles. If the chosen directory needs administrator access, it shows an exact, quoted command to copy; it never invokes sudo.

It looks for an existing `deadbolt` in the same places the app looks for an agent binary (`binary::search_dirs`): PATH, then `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin` and `~/.cargo/bin`, which a Finder launch's PATH lacks. Directories that can't be read count as not having one. The scan and the install run off the UI thread. What it finds is this app's link, a link to a moved Deadbolt, Homebrew (a Cellar link), Cargo (`.cargo/bin`), or another install. A link is ours by its target's shape, `<anything>.app/Contents/Helpers/deadbolt`, whether or not the target still exists; the installer repoints it at this app (a new link renamed over the old one) or gives the `sudo ln -sfh` to do so. No other file or symlink, including a dangling one, is replaced: remove the old command through its installer, then Check again. A copy running from a disk image (`/Volumes`) or under App Translocation refuses to link and says to move Deadbolt to Applications first.

## Shipping the app

Build an ad-hoc-signed development bundle on a Mac worker:

```sh
hivemind run --kind cargo --fetch .lab-output -- bash crates/app/scripts/bundle.sh
# Universal, after installing aarch64-apple-darwin and x86_64-apple-darwin:
hivemind run --kind cargo --fetch .lab-output -- bash crates/app/scripts/bundle.sh --universal
```

The script builds both release binaries with `--locked`, assembles into a temporary directory, generates the icon, signs ad hoc and checks the plist, signature, bundled CLI's `--version` and app's headless `--list-scenes` before moving the bundle into `.lab-output/Deadbolt.app`. An optional final argument selects a fresh output path; an existing output is refused. Native is the default to reuse the build cache; universal builds both Rust targets and combines each executable with `lipo`. These bundles aren't distribution releases.

Dax's `publish.yml` currently builds four CLI targets, then `packages/cli/script/release.ts` publishes tarballs, checksums and a Homebrew **formula**. `site/public/install` consumes those CLI tarballs. To add the app, introduce a macOS bundle job in the same publish mode, call this script, sign and notarize, then pass its app archive/DMG to the publish job. Keep the CLI artifacts and installer contract. The release script must upload the app even when the `v<version>` release already exists; its current existence check skips all uploads on reruns.

Remaining release work, with Anomaly's identities and Dax's pipeline:

- Developer ID signing with hardened runtime on `fleet role releaseHost`, replacing the development signatures inside-out; verify the signing identity and entitlements there.
- Notarize and staple every app and DMG, then assess both with Gatekeeper before publishing.
- Add a Sparkle-style signed update feed and updater integration. Upload and verify artifacts before publishing the feed.
- Add the Homebrew **cask** (`brew install --cask anomalyco/tap/deadbolt`, or `brew install --cask deadbolt` after tapping), alongside the existing CLI formula.
- Add a Mac download button to deadbolt.pw. Site publishing needs Dax's approval.

Signing identities, notarization, updater integration and publishing are deliberately left to that release work.
