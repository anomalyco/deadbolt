# Signing Deadbolt updates

**Decision open ([#112](https://github.com/anomalyco/deadbolt/issues/112)).** Can an installer verify who authorized a release, even if the download host supplied both the manifest and the archive? Today, the [workflow](../../.github/workflows/release.yml) checks inter-job `SHA256SUMS`, attests archives on GitHub and publishes with OIDC. The [updater](../../crates/cli/src/update.rs) checks HTTPS, refuses redirects, restricts file URLs to `/release/deadbolt/files/` on the same origin, and checks size and SHA-256. None authenticates the manifest: the host can change the file, digest and sequence together. Linux ships; there is no Windows target today.

## What both options sign

Sign the exact bytes of `https://anoma.ly/release/deadbolt/<artifact>/<channel>.json`: schema, app, artifact, channel, sequence, version, each target's URL/size/SHA-256, rollout, required flag, notes and distributions. Signing just the tarball doesn't authorize making it current.

The [release service](https://github.com/anomalyco/release/blob/HEAD/docs/protocol.md) assigns sequences and writes these manifests; `record-brew` changes them again. It would need to stage a revision, then publish those exact bytes and their proof together. The signer must check targets against verified build outputs and approve the sequence and intended operation, not blindly sign the service response. Re-sign rollouts, rollbacks and distribution changes. Isolate signing from [the publisher](../../.github/release/release-service.sh), which downloads and executes the service's `client.sh`.

| | Pinned [minisign](https://jedisct1.github.io/minisign/) key | [Sigstore/cosign](https://github.com/sigstore/cosign/blob/main/doc/cosign_verify-blob.md) keyless |
| --- | --- | --- |
| Custody | Maintainers keep a long-lived Ed25519 secret and recovery copy. Give only the signer access; separate dev and stable keys. A leaked key can sign outside CI. | No stored release secret. Actions OIDC authorizes a short-lived Fulcio certificate; Rekor records the signature. Pin issuer `https://token.actions.githubusercontent.com` and a distinct protected signing workflow in `anomalyco/deadbolt`; allow `refs/heads/dev` for dev, `refs/heads/production` or the matching protected `v<version>` tag for stable. The publisher must not match that identity. |
| Offline | `minisign -Vm stable.json -P "$PIN"` verifies the adjacent `.minisig` with an independently trusted public key. | `cosign verify-blob` needs the manifest, saved bundle, expected issuer/identity and independently authenticated Sigstore roots. Verify signature, certificate at trusted signing time and log inclusion proof without contacting the log. |
| Rotation | Deliver the next pin under the old one, overlap signatures, then retire the old pin. If the only trusted key is stolen, distribute its replacement out of band. | Keys rotate per run. Refresh roots via authenticated Sigstore updates; ship new roots or identity policy before relying on them offline. |

The choice is between custody of a reusable release key and dependence on GitHub/Sigstore identity and root updates. Neither protects against an authorized signer approving malicious build output.

## Where to verify

- **CLI.** Verify before `decide` or `check_sequence`, then check the target tarball before extraction. Keep release macOS CLI/helper Developer ID checks; source-built CLIs and Linux lack that gate. [The shell installer](../../site/public/install) checks feed size/hash or, for `DEADBOLT_VERSION`, only GitHub's `SHA256SUMS`. Mirror the signed manifest and proof on the stable tag; verify the requested version and target before `tar` or `deadbolt --version`. A pin in `curl | sh` can't authenticate the script itself: provide an independently trusted verifier and pin/roots for first install.
- **Desktop.** The bundled CLI updates `Deadbolt.app` from the `desktop` universal zip, not the DMG. Verify the signed target first; retain zip/link checks, deep `codesign` against [the app requirement](../../crates/app/update-requirement.txt) and Gatekeeper before swapping. Verify the DMG before mounting; render Homebrew cask/formula hashes from verified manifests. Managed installs still update through their manager.
- **Extension.** `deadbolt browser install --extension-dir <dir>` registers a directory; `deadbolt update` and `browser switch` fetch `chromium` or `chromium-standalone`. Verify the selected zip before staged extraction and rename. Neither the fixed extension ID nor `.deadbolt-extension` (top-level names) authenticates a directory. To check an unpacked copy offline, compare every path, type and file digest against the verified zip; reject extra, missing or linked entries, allowing only the updater's marker as an extra regular file. Standalone settings offer a download, not verification.
- **Downgrade.** The [current high-water mark](../releasing.md#updater) in `release-sequences.json` is per artifact/channel. Advance it only after authentication. `--allow-rollback` may accept an older *signed* revision, never bypass verification; a deliberate rollback signs an older version at a new, higher sequence. First installs and offline clients can't prove freshness. Publish proofs before shipping enforcing clients with a trusted sequence floor; never fall back to unsigned feeds. Old clients remain unprotected until replaced through a trusted path.
